# Artifact Center — 优化问题审计

> 最后更新：2026-07-30  
> 用途：记录可观察的问题、触发条件、影响、根因、修复状态与验收证据。  
> 边界：本文件是优化工作的事实清单，不替代 PRD、ROADMAP 或 ADR。

## 1. 如何阅读

只写“需要优化性能”或“缺少 E2E”无法指导开发，也无法证明完成。本审计中的每一项必须回答：

1. **具体表现**：用户、管理员或开发者实际会看到什么。
2. **触发条件**：在什么数据量、网络、权限或操作路径下出现。
3. **影响**：会导致等待、误判、泄露、数据错误还是运维风险。
4. **根因与证据**：对应到代码、配置、构建产物或测试。
5. **完成标准**：什么证据足以把该项标记为完成。

状态约定：

| 标记 | 含义                                     |
| ---- | ---------------------------------------- |
| ✅   | 已修复，并有自动化测试、构建或运行态证据 |
| 🟡   | 已缓解，但根因或关键验收证据尚未完成     |
| ❌   | 尚未实现，或目前没有任何有效保障         |

测试通过只证明测试覆盖到的行为，不代表真实数据库、真实浏览器、生产代理或大文件压力场景已经验证。

## 2. 当前可复现的主要问题

### 2.1 性能与容量

#### PERF-01：首次进入应用仍需下载过大的前端基础包

- **状态**：🟡 页面 lazy + 未登录不挂载 UploadManager/任务条（Grok 2026-07-30）；首屏体积仍需用构建报告量化。
- **具体表现**：用户首次打开站点时，登录框或应用列表可能长时间停留在空白/加载态；低速内网、移动热点和低性能终端上更明显。
- **触发条件**：浏览器无缓存、发布新版本后缓存失效，或用户首次访问。
- **影响**：延迟“看到可操作界面”的时间；页面级懒加载无法消除基础包本身的解析和执行成本。
- **根因与证据**：生产入口为 **371.45 kB / 117.04 kB gzip**，HTML 还会 `modulepreload` **281.18 kB / 94.97 kB gzip** 的公共依赖；初始依赖图合计约 **652.63 kB / 212.01 kB gzip**。虽然单文件均低于 500 kB、Vite 不再警告，但冷启动仍会下载两者，不能把“拆成两个文件”当作“首屏已减重”。
- **已做工作**：页面级 `lazy/Suspense` 已把历史主包从约 944 kB 降到约 650 kB，并把入口与公共依赖拆成独立缓存单元。
- **完成标准**：用 bundle analyzer 确认组成；拆出非首屏依赖或按认证状态加载 Provider；用冷缓存浏览器记录首屏实际传输量、解析时间和可交互时间，达到约定预算。

#### PERF-02：字体资源会吞掉远超业务代码的首访流量

- **状态**：🟡 系统栈优先 + 仅引用 4 个 TTF（2 中文 + 2 mono），`font-display: optional`（Grok 2026-07-30）；`public/fonts` 文件未删除，冷缓存网络面板证据待补。
- **具体表现（缓解后）**：正文默认系统 UI 字体；品牌/等宽字体仅在可选加载成功时增强。
- **原触发条件**：冷缓存访问同时注册多档 CJK/Mono 字重。
- **影响**：原先潜在数十 MiB 字体下载；现引用面大幅缩小。
- **根因与证据**：历史 `fonts.css` 注册 9 个 TTF 且 tokens 将 Alibaba 置于栈首。
- **已做工作**：tokens 系统字体优先；fonts.css 仅 Regular/Bold（CJK）与 Regular/SemiBold（Mono）；`font-display: optional`。
- **完成标准**：冷缓存浏览器证据显示首屏字体传输量达标；可选 WOFF2 子集。

#### PERF-03：512 MiB 上传限制并不等于 512 MiB 内存上限

- **状态**：🟡 已限制请求大小，尚未流式化。
- **具体表现**：一个大文件上传时 API 进程内存会突然上升；多个用户并发上传可能触发频繁 GC、响应变慢或容器被 OOM 杀死。
- **触发条件**：接近 512 MiB 的文件，尤其是多个并发上传。
- **影响**：上传失败会让用户误以为网络问题；同一 API 实例上的登录、搜索和下载也会受拖累。
- **根因与证据**：`apps/api/src/routes/artifacts.ts` 依次执行 `parseBody()`、`file.arrayBuffer()`、`Buffer.from(...)`，再交给 `saveUploadBuffer`，处理期间可能同时存在 multipart、ArrayBuffer 和 Buffer 的内存副本。
- **已做工作**：API 在 multipart 解析前限制整个请求体为 513 MiB，文件本身限制为 512 MiB；Nginx 同步配置 `client_max_body_size 513m`。
- **完成标准**：上传改为流式写入临时文件并边写边计算 SHA-256；压测并记录 1 个和多个 512 MiB 上传时的进程峰值内存，峰值不随文件大小线性增长。

#### PERF-04：应用、制品和发布列表没有统一分页

- **状态**：主浏览页面已完成（2026-09-10）。ADR-0020 锁定游标分页；旧兼容调用及部分管理选择器仍保留全量语义。
- **具体表现**：目录规模变大后，打开应用列表或应用详情会越来越慢；浏览器一次渲染大量行，滚动卡顿，API 响应体持续膨胀。
- **触发条件**：数百个 Application，或单个 Application 下积累数百到数千个 Artifact/Release。
- **影响**：查询、JSON 序列化、网络和 React 渲染成本同时增长；无法稳定定义“下一页”，也不利于移动端。
- **根因与证据**：原集合接口无读取上限，目录重复加载完整应用用于计数，详情预取全部历史。现以分页、独立汇总和概览查询修复，见 [容量测量与回归记录](performance-2026-09-10.md)。
- **完成标准**：ADR 锁定分页语义；集合 API 返回稳定游标或页信息；前端支持加载更多/翻页；数据库集成测试覆盖新增、删除发生在翻页期间的边界。

#### PERF-05：多字段前后通配搜索在数据量上升后会退化

- **状态**：目标规模已完成索引与查询优化（2026-09-10）：300 应用、90,000 制品，版本搜索 P95 17.54ms，无结果查询 P95 14.84ms。单字符搜索 P95 248.15ms，仍高于具体关键词，且易受机器负载影响。见 [实测记录](performance-2026-09-10.md)。
- **具体表现**：用户输入名称、包名或版本片段后，搜索结果迟迟不出现；字符越通用，扫描行数越多。
- **触发条件**：Application/Artifact 数量增长，查询形如 `%关键字%`，并同时匹配多个字段。
- **影响**：全局搜索和应用筛选是“查找制品”主旅程入口，延迟会直接让用户回到询问开发者的旧流程。
- **根因与证据**：原全局查询的跨表 OR 阻碍索引筛选，对制品说明反复匹配。已拆分先鉴权的候选分支，增加单个 pg_trgm 表达式索引并复核逐字段匹配；原始 JSON 包含真实 PostgreSQL 执行计划。
- **已做工作（Codex · 2026-07-30）**：搜索与应用目录只选择会返回给客户端的 Application 列；全局搜索的 Artifact 结果不再读取或传输 `sha256`、`parsedMeta`、`buildMeta`。结果上限继续限制为应用 40、制品 60，未引入新索引或改变搜索契约。
- **EXPLAIN 基线步骤**：在接近目标规模的 PostgreSQL 环境，以已登录用户可见的数据执行下列查询并保存完整计划、`Execution Time`、`Rows Removed by Filter` 与 `shared hit/read`；分别测高频词和稀有词，每种至少 20 次并记录 P95。`EXPLAIN (ANALYZE, BUFFERS) SELECT id, name, package_name, updated_at FROM applications WHERE name ILIKE '%关键词%' OR package_name ILIKE '%关键词%' OR owner_name ILIKE '%关键词%' ORDER BY updated_at DESC LIMIT 40;`；制品侧以 `artifacts` 与 `applications` 的同等可见性 join、`version/filename/build_number/release_notes` 条件、`ORDER BY artifacts.uploaded_at DESC LIMIT 60` 执行。若扫描行数或 P95 不可接受，再按 ADR-0006 评估 `pg_trgm` migration。
- **完成标准**：生成接近目标规模的数据；记录现状执行计划和 P95；按 ADR-0006 增加 trigram 索引或调整搜索策略；以相同数据和查询证明扫描行数与延迟达标。

### 2.2 安全与权限

#### SEC-01：数据库中的分享令牌是可直接使用的明文凭证

- **状态**：🟡 新链接已改为 HMAC 摘要存储；遗留明文列迁移升级路径已实现，待生产库跑 migration 并清空遗留 `token` 列后可标 ✅。
- **原具体表现**：一旦数据库备份、只读账号或 SQL 日志泄露，拿到 `share_links.token` 的人无需登录即可打开仍有效的分享链接并下载制品。
- **触发条件**：数据库或备份内容被非预期人员读取，且链接未过期、未吊销。
- **影响**：数据库泄露会直接升级为制品泄露，无法像密码哈希那样降低离线数据的利用价值。
- **已修复部分（Grok · 2026-07-30）**：
  - 新增 `token_hash`（HMAC-SHA256 + `SHARE_TOKEN_PEPPER`），创建只写 hash，明文 token 仅在 201 响应返回一次。
  - `resolveShare` 优先按 hash 查找；命中遗留明文 `token` 时就地升级为 hash 并清空明文。
  - 列表/吊销不再回传可重放明文；前端仅展示 `tokenPrefix`，无法再次复制完整链接。
  - 迁移 `0011_share_token_hash.sql`；生产要求 `SHARE_TOKEN_PEPPER` ≥ 32 字符。
- **验证证据（主工作树，Grok 2026-07-31）**：
  - `npx vitest run src/__tests__/share-token.test.ts src/__tests__/env.test.ts` 通过。
  - 真实 PG：`npm run db:migrate` 已应用 `0009`–`0011`（含 token_hash）。
  - `.\scripts\smoke-p0.ps1`：health/login/create-share/resolve 无回显/list 无明文 → **PASS=7**。
  - 公开解析响应已去掉 `token` 字段。
- **剩余风险**：最终 `DROP COLUMN token` 仍可选；生产须独立配置 `SHARE_TOKEN_PEPPER`。
- **完成标准**：只在创建时返回原始令牌，数据库仅保存带服务端 pepper 的不可逆摘要；迁移和轮换策略覆盖已有链接；测试证明数据库内容不能直接作为公开 URL 凭证。

#### SEC-02：JWT 在有效期内无法立即撤销

- **状态**：❌。
- **具体表现**：用户被停用、修改密码或管理员怀疑令牌泄露后，旧令牌仍可能继续访问，直到 7 天有效期结束。
- **触发条件**：旧令牌已经签发，之后发生密码修改、权限收回、账号处置或密钥疑似泄露。
- **影响**：安全响应窗口最长可达令牌剩余有效期；“重置密码”不能保证其他设备立即退出。
- **根因与证据**：当前认证只验证 JWT 签名和过期时间，没有 token version、`jti` denylist 或短 access token + refresh token 轮换。
- **完成标准**：锁定撤销模型；账号状态、密码变更和角色变更能使旧凭证失效；自动化测试覆盖被撤销令牌和多实例一致性。

#### SEC-03：登录和公开分享入口没有速率限制

- **状态**：❌。
- **具体表现**：同一来源可连续尝试密码或高频访问公开分享解析/下载接口；服务端不会返回明确的 `429`。
- **触发条件**：自动化撞库、令牌猜测、恶意重复下载或错误客户端重试。
- **影响**：增加账号被攻破、带宽耗尽和 API 资源被挤占的风险。
- **根因与证据**：路由与代理配置中没有按来源、账号或分享令牌实施 rate limit，也没有可信代理/IP 取值策略。
- **完成标准**：明确内网代理拓扑；登录按账号+来源限速，公开下载按来源+令牌限速；返回 `Retry-After`；测试正常突发、超限和代理头伪造。

#### SEC-04：上传文件没有恶意内容扫描状态

- **状态**：❌。
- **具体表现**：任何拥有上传权限的人都可以发布带恶意载荷的 APK、EXE 或 ZIP，下载页仍会把它当作正常制品展示。
- **触发条件**：账号被滥用、构建机被入侵或上传者误传受感染文件。
- **影响**：Artifact Center 可能成为组织内恶意文件的可信分发入口。
- **根因与证据**：Artifact 没有 pending/scanning/clean/rejected 状态，也没有隔离区和扫描器接口。
- **完成标准**：新增扫描状态与隔离存储语义；未通过扫描的文件不能公开下载或标记 latest；审计记录扫描结果；用无害测试样本验证拒绝链路。

### 2.3 可靠性与数据一致性

#### REL-01：过大 multipart 请求曾在业务校验前消耗资源

- **状态**：✅。
- **原具体表现**：攻击者或错误客户端可以持续发送超大请求；API 要到 multipart 解析后才知道文件过大，内存、CPU 和网络连接已被占用。
- **修复与证据**：`apps/api/src/index.ts` 在上传路由前应用 Hono `bodyLimit`；Nginx 同步限制；`apps/api/src/__tests__/upload-body-limit.test.ts` 覆盖边界。

#### REL-02：相同文件名的并发上传曾可能写到同一个存储键

- **状态**：✅。
- **原具体表现**：同一 Application、版本和文件名同时上传时，后到请求可能覆盖先到请求的磁盘文件，而数据库行仍分别保存各自元数据。
- **修复与证据**：存储键加入随机 UUID；上传与存储测试覆盖不同请求生成不同目标。

#### REL-03：同一 Application 可重复上传完全相同的内容

- **状态**：🟡 代码路径已修复，真实 PostgreSQL 并发验收待补。
- **原具体表现**：用户重复点击、取消后重试或两人同时上传同一文件，会产生内容 SHA-256 相同的多条制品记录并重复占用磁盘；仅比较文件名无法发现改名后的重复文件。
- **修复与证据**：前端在上传前调用 `/applications/:appId/artifacts/duplicate-check`；服务端写文件后在事务内用 applicationId+sha256 的 advisory lock 再次检查，避免两个并发请求同时通过预检；新增 `(application_id, sha256)` 索引和迁移 `0009_hot_arclight.sql`。前端/API 单元测试均已通过。
- **剩余风险**：当前路由测试使用 mock DB，尚未证明真实 PostgreSQL advisory lock 的并发顺序、迁移耗时和既有重复数据情况。
- **完成标准**：临时 PostgreSQL 集成测试并发上传同一内容，只允许一条记录且失败请求清理临时文件；迁移前审计历史重复数据；记录索引创建和查询执行计划。

#### REL-04：浏览器“取消上传”不保证服务端立即停止

- **状态**：🟡 客户端体验已改善，服务端语义未闭环。
- **具体表现**：用户点击取消后界面显示已取消，但请求体可能已经到达服务端，API 仍可能继续解析、写盘和入库；随后重试可能遇到重复内容。
- **触发条件**：取消发生在请求已经发送、代理已缓存请求体或服务端完成接收之后。
- **影响**：用户对最终状态产生误判；浪费磁盘和 CPU；取消与重试之间存在竞态。
- **根因与证据**：客户端 AbortController 只能终止本地等待，当前上传没有服务端 upload session、幂等键和显式取消协议。
- **已做工作**：支持取消、取消后重试、离页提醒，并防止旧请求结果覆盖重试状态；重复内容复核降低了重复入库影响。
- **完成标准**：定义 upload session 与幂等语义；服务端能标记并清理取消会话；断线、取消、重试和代理缓冲场景有集成测试。

#### REL-05：存储配额目前不能阻止磁盘被写满

- **状态**：🟡 单 API 进程已具备硬配额与磁盘余量门禁；多实例共享预留、告警与运维恢复演练仍待完成。
- **具体表现**：设置页可能显示用量，但上传不会在接近配额时拒绝；磁盘写满后上传失败，健康检查可能转为未就绪，其他写操作也受影响。
- **触发条件**：持续上传大文件、保留清理未及时执行，或主机磁盘本身空间不足。
- **影响**：平台级不可用，并可能影响数据库或同机服务。
- **根因与证据**：原先保留策略和用量展示没有形成上传前容量预留、硬配额和告警闭环。
- **已做工作（Codex · 2026-07-30）**：上传在写入文件前读取 `retention_settings.storage_quota_bytes`、当前制品用量和 `statfs` 可用空间；超配额、低于 `STORAGE_MIN_FREE_BYTES`（默认 512 MiB）或无法读取磁盘数据时均返回 `507`。同一 API 进程会为待写入文件预留容量，成功入库或失败清理后释放；设置 API 允许管理员更新 `storageQuotaBytes`。`upload-capacity.test.ts` 覆盖超配额、低磁盘、并发预留和存储数据不可用。
- **完成标准**：上传前原子预留容量；达到软阈值告警、硬阈值拒绝；并发上传不会共同越过上限；运维文档包含扩容和清理恢复步骤。

### 2.4 数据真实性

#### DATA-01：运行时代码仍有 Mock 命名和模拟解析残留

- **状态**：🟡 已移除两处会误导用户或维护者的活跃 Mock，文件内容解析仍未真实化。
- **修复前表现**：上传选择器用演示 Application ID 把真实目录中的同名记录标成“置顶/最近”，即使用户从未置顶或访问；成员设置虽然读取真实 API，却从 `mock-members.ts` 获取角色定义，让维护者难以判断数据来源。
- **已修复部分**：角色定义迁入 `member-roles.ts`；选择器移除伪造置顶，根据服务端 `updatedAt` 展示“最近更新”，并用纯函数测试证明排序不修改原目录数组。
- **剩余表现**：上传预解析仍调用 `mockParseFile`，只能按文件名猜测版本、包名和平台，不能读取 APK/AAB 清单或签名。旧 store/mock 死链已于 2026-09-10 经入口依赖检查后移除，见 [代码整理记录](code-maintenance-2026-09-10.md)。
