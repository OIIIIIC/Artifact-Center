# 数据量性能验证 · 2026-09-10

目标：300 个应用，每个应用 300 个制品和发布，共 90,000 个制品、90,000 个 Release。使用独立的本地 PostgreSQL 16 数据库和合成说明文本，不改写用户业务数据。测试的是单请求数据量，非并发压力。

## 已复现的问题

`npm test --prefix apps/api -- --run src/__tests__/catalog-scale.integration.test.ts` 首次运行失败：请求 24 个应用却返回 1,000 个，响应 1,426,810 字节；单应用请求 24 个制品却返回 300 个，响应 584,003 字节。该回归现在通过。

全局搜索在 90,000 条制品下的版本/无结果查询中位数为 692.04 / 770.27ms；带 `--check` 的性能脚本也实际失败于 250ms 本地中位数预算。先拆分跨表匹配分支，降至约 230 / 244ms；再加入 pg_trgm 候选索引，降至下表水平。

## 最终测量

实际 Hono 路由调用 PostgreSQL，包含鉴权、查询、映射、JSON 序列化及读取响应文本；不包含浏览器渲染、真实网络往返或 gzip。每条路径交错执行，2 次预热、20 次采样，记录中位数及 P95。旧全量路径与分页路径使用相同数据；旧发布路径已受益于本次线性分组，故其时间比较是保守基线。

| 路径               |             原全量响应 |                 当前首批响应 |  当前中位数 / P95 |
| ------------------ | ---------------------: | ---------------------------: | ----------------: |
| 应用列表           |     300 个 / 385,067 B |             24 个 / 31,010 B |    9.44 / 10.58ms |
| 目录计数           |       依赖完整应用目录 |               汇总 / 1,332 B |     4.06 / 4.68ms |
| 制品历史           |     300 条 / 603,203 B |             30 条 / 60,520 B |     7.41 / 8.90ms |
| 发布历史           |     300 条 / 545,315 B |             20 条 / 36,550 B |     7.73 / 9.23ms |
| 详情概览           | 等待完整制品与发布历史 | 最近 3 条 + latest / 8,065 B |     4.45 / 6.08ms |
| 全局搜索 `1.0.299` |        中位数 692.04ms |                返回 8 个制品 |   13.89 / 17.54ms |
| 全局搜索无结果     |        中位数 770.27ms |                    返回 0 条 |   11.28 / 14.84ms |
| 单字符搜索 `1`     |                      — |      返回 16 个应用/制品结果 | 219.81 / 248.15ms |

应用首批响应减少约 92%，制品约 90%，发布约 93%。概览不再等待完整历史。全局搜索旧基线采样为 5 次，最终为 20 次；时间受本机缓存与负载影响，这些数字不是线上延迟保证。完整版本号与无结果查询的收益明显，低选择性的单字符搜索仍慢一些。

一次与完整测试/类型检查同时运行的测量中，单字符搜索中位数升至 556.93ms，触发 250ms 本地预算失败。上表为检查结束后单独运行的最终测量，预算通过；这说明该预算依赖测量环境空闲，不能作为负载下的延迟承诺。

原始数据及执行计划：[最终记录](performance-2026-09-10.json)、[搜索旧基线](performance-search-before-2026-09-10.json)。历史页计划使用 `artifacts_application_history_idx`，读取 LIMIT 所需的 31 条（含判断下一页的一条）；无结果候选查询使用 `artifacts_search_trgm_idx`，避免逐行扫描全部制品说明。

## 回归与浏览器验证

- API：上限、总数、项目/产品和关键词筛选、普通用户权限及收藏；微秒时间、同名应用、锚点删除；较早制品被手动标记 latest；Release 制品计数与类型。
- 全局搜索：两个候选分支去重，先鉴权后 LIMIT，字面特殊字符，拼接字段边界复核。
- 前端：翻页不追加旧页 DOM；切换筛选重置游标；失败后可返回；离开详情返回列表恢复当前页。
- 浏览器：300 个应用只渲染 24 张卡片，第二页仍为 24 张且无重复；搜索跨页找到应用 300；制品每页 30 行且翻页不重复；查找历史版本成功；产品管理仍显示 30 个应用的完整计数。

最终 `npm run verify` 通过：前端 135、API 111、MCP 6 项测试，共 252 项；代码检查、前后端类型检查与前端生产构建通过。本地业务数据库已应用 0024/0025 索引迁移，业务记录数量保持 18 个应用、13 个制品、14 个发布。

## 复现

先创建一个空的本地 PostgreSQL 数据库，名称必须以 `artifact_center_bench_` 开头。进入 `apps/api`，设置 `BENCH_DATABASE_URL` 为该专用库连接串，运行：

```text
npx --no-install tsx scripts/benchmark-catalog.mts --check
```

脚本运行所有迁移并创建合成数据；数据库非空时拒绝播种。显式加 `--reuse` 可在同一专用验证库重新测量。`BENCH_REPORT_PATH` 指定 JSON 输出；`BENCH_SERVE=true` 可启动隔离浏览器验收 API（4018），前端通过 `API_PROXY_TARGET` 指向它。脚本不执行清库操作。

本次验证只涉及元数据。二进制下载/上传、并发极限、首访资源大小，以及超过当前目标规模的全文搜索仍需各自测量。旧兼容集合接口和部分选择器仍保留全量语义，不能把主页面改善表述为所有接口都已分页。
