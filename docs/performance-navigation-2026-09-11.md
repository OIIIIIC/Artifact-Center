# 应用导航性能测量（2026-09-11）

## 结论

复现了用户补充的主要路径：**工作台刷新 → 首次点击左侧“应用”**。本机开发版本需要约 775～784ms 才出现应用卡片，首次进入期间最大长任务 220～231ms；正式构建预览需要约 262～327ms，仍记录到 75～92ms 的长任务。首次进入的代码加载、数据请求和集中渲染值得优先优化。

已经进入应用列表后的目录切换表现明显更好。真实 18 个应用的重复切换、快速切换和同项目应用切换，采样窗口内均没有超过 50ms 的长任务。300 个应用的合成场景存在少量较长帧间隔，但未发现目录重新清空或快速切换最终显示错误结果。

本轮为测试与定位，没有修改应用性能实现。数值来自本机小样本，不能解释为线上所有设备的保证。

## 条件与测量口径

- 工作目录基于 `42da2e8f`，存在其他进行中的工作区修改；开发服务 5178，临时正式构建预览 5180。
- Chromium，1440×960，未人为降低 CPU 速度。正常采样时空闲帧间隔中位数约 8.3ms。
- 实际业务数据：24 个产品、18 个应用。合成数据：30 个产品、60 个项目、300 个应用，每个应用的制品数量字段为 300；没有创建 9 万条数据库记录或下载制品文件。
- 工作台首次进入与补充鼠标测试使用可信鼠标事件；批量树切换使用 DOM click 驱动同一事件处理逻辑。
- “卡片出现”指结果节点已挂载，首次进入测试另检查节点有非零高度；不等于动画完全结束或像素呈现时间，也不是 INP。
- 帧间隔来自 requestAnimationFrame 回调，长任务来自 PerformanceObserver。较长帧间隔不一定全部由 JavaScript 长任务造成，也不能直接换算成 GPU FPS。
- 浏览偏好和访问记录写入由隔离浏览器拦截；偏好读写保持一致。实际目录和应用接口照常读取本地 API。Playwright 路由拦截会禁用 HTTP 缓存，因此首次加载数据属于该条件下的冷进入测量。
- 前期不一致偏好模拟引起重复保存，另一次未保持前台的鼠标测量出现约 1 秒回调间隔；两组结果均作废，不进入结论。

## 重点：工作台刷新后进入应用

每个版本做两轮“工作台整页重新加载 → 应用 → 工作台 → 应用”。等待工作台标题出现后约 700ms 再点击“应用”，每次观察至少 1500ms。

| 场景                     | 卡片出现（两轮） | 最大帧间隔（两轮） | 最大长任务（两轮） |
| ------------------------ | ---------------- | ------------------ | ------------------ |
| 开发版，刷新后首次进入   | 783.5 / 774.8ms  | 246.2 / 228.1ms    | 231 / 220ms        |
| 开发版，再次进入         | 338.4 / 339.8ms  | 83.3 / 110.3ms     | 78 / 104ms         |
| 正式构建，刷新后首次进入 | 326.7 / 261.9ms  | 101.8 / 82.9ms     | 92 / 75ms          |
| 正式构建，再次进入       | 114.4 / 121.3ms  | 54.5 / 50.4ms      | 未观察到           |

第一轮开发版的时间线：

1. 点击后约 331～338ms 才开始请求产品、项目、目录汇总和第一页应用。
2. 约 357ms 出现“全部应用”标题，此时卡片尚未挂载。
3. 相关请求在约 367～462ms 结束，卡片在约 784ms 才出现。
4. 约 547ms 开始的一次 231ms 长任务覆盖了卡片出现前的主要停顿。

第一轮正式构建中，接口约在点击后 107～110ms 启动、139～189ms 结束，卡片约 327ms 出现。第二次进入不再读取这些接口，但仍需挂载页面内容。

这些观测说明等待包含两个阶段：首次加载页面代码后才发起请求，以及数据到达后的渲染工作。不能把整段等待全部归因于网络或数据库。采样未观察到整个 AppLayout 消失，工作台在新页面准备期间仍可见；切换到应用后有标题先出现、卡片稍后出现的阶段。

开发版观察到汇总与分页读取重复启动；正式构建没有对应重复。项目启用了 React StrictMode，该差异与开发期额外执行相符，不能据此认定正式环境会重复加载目录。

### CPU 采样补充

另做了一次开发版首次进入的 1ms 间隔 Chromium CPU 采样：

- 一个 `renderRootSync` 调用树累计约 304ms，同步更新调用树累计约 379ms。它们是包含子调用的累计样本，不能相加，也不等于单次长任务。
- 目录组件恢复 `scrollTop` 的 layout effect 在两个调用栈中分别采到约 37ms、17ms；动画库 `measureScroll` 约 23ms。
- JSX/图标创建、DOM 创建及 React 开发检查也占有样本。

这支持优先检查集中渲染及同步布局工作，但尚未通过逐项修改的对照试验证明某一个函数是唯一根因。CPU 采样本身有开销，其数字不与上表直接混用。

慢接口快速切换结束后，最终标题为最后选择的“容量产品18”，10 张卡片全部属于该产品。用户持续切换时中间请求来不及完成是预期现象，不能把中间未就绪次数当成卡死次数。

缓存后产品切换仍会保存浏览偏好，并刷新 workspace 查询：真实数据 16 次切换产生 16 次 workspace GET，未重新读取目录。这是可以合并的后台请求，不是目录清空重载。

### 可信鼠标点击对照

固定在合成数据的两个已缓存产品之间切换，采用正常动画 → 减少动态效果 → 恢复正常动画，每组 4 次。每次点击前保持页面前台，全部记录为 `trusted=true`、`visibility=visible`。

| 模式           | 卡片响应范围 | 最大帧间隔 | >50ms 长任务 |
| -------------- | ------------ | ---------- | ------------ |
| 正常动画 A     | 60.7～72.5ms | 30.8ms     | 0            |
| 减少动态效果 B | 41.8～53.9ms | 35.7ms     | 0            |
| 正常动画 A     | 55.8～82.3ms | 27.1ms     | 0            |

每组捕获的 click 事件时长均为 24ms（Event Timing 的量化观测值，并非整页 INP）。这个小范围对照没有复现严重卡顿，不能证明去掉动画能解决首次进入问题。

## 后续优化顺序

1. 优先处理“工作台 → 应用”的首次进入：在合适的空闲/导航意图时机预加载页面代码，并让必需数据尽早并行准备；避免把全部准备工作压到点击之后。
2. 减少首屏卡片和目录的重复渲染、同步布局读写，单独核对滚动位置恢复与嵌套高度动画的布局开销。保留平滑过渡，以最大长任务和连续帧间隔验证改善。
3. 合并快速导航期间的偏好保存和刷新请求。该项能减少无效工作，但当前证据不足以把它当成首次卡顿的主要原因。

尚未实施这些优化；应使用同一复现路径做修改前后对照，不能以删除动画或仅缩短加载文案作为性能改善。
