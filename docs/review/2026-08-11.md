#### 问题 1：[P1] 默认选中用户的成员状态始终为空

文件：`src/features/settings/access-permissions-panel.tsx:58-79`

`selectedUser` 会在 `selectedUserId` 为空时回退到第一个非管理员，但成员关系的查找仍使用空的 `selectedUserId`。因此权限页面首次加载时，已有成员关系被展示为“未配置”，应用负责人也不会被锁定；管理员若未先手动点击用户，就可能基于错误状态提交批量变更。应使用 `selectedUser.id`（或在用户数据加载后初始化 `selectedUserId`）作为成员查找键，并覆盖负责人场景。

#### 问题 2：[P2] 权限页面按应用逐个请求成员列表，应用规模增长后会形成请求风暴

文件：`src/features/settings/access-permissions-panel.tsx:61-68`

页面打开后会为每个应用并发调用一次 `/applications/:id/members`，而每个响应都包含该应用全部成员。当前页面需要的只是“所选用户在各应用中的角色”，在几十到上百个应用时会产生大量网络请求和重复数据传输，也会让加载状态无法准确反映完整性。建议增加一个管理员专用的按用户批量查询接口（一次返回应用 ID、角色和 owner 标记），并为它补充分页或上限策略。

#### 问题 3：[P2] 新增批量授权接口没有自动化测试

文件：`apps/api/src/routes/settings.ts:40-207`

`/settings/access-grants` 负责批量写入访问控制，但现有测试中没有覆盖该路由。至少应覆盖：非管理员拒绝、查看者不能被授予维护者、负责人不能降级或移除、未知应用导致整批不写入、重复应用 ID 与成功写入/审计记录。这样才能防止后续调整权限中间件或 SQL 时发生静默越权。
