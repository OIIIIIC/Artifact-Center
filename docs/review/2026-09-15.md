#### 问题 1 [P2]：保留详情页签后，返回制品历史不会刷新过期数据

- 引入提交：`9d405407`。
- 位置：`src/features/applications/detail-tab-content.tsx:13`、`:17`；消费者 `src/features/applications/application-history-page.tsx`。
- 触发：打开制品页签后切到概览，停留超过查询的 30 秒新鲜期，期间其他用户或发布工具上传新版本，然后切回制品页签。
- 原因：访问过的页签通过 `forceMount` 加 `hidden` 常驻；历史查询没有接收 `active`，也没有在重新激活时刷新。原先卸载/挂载所触发的过期查询刷新不再发生。当前页面没有窗口焦点变化时，会继续显示旧版本列表。
- 复现：用真实 `DetailTabContent`、`ApplicationHistoryPage` 和 QueryClient，接口初始返回 v1；隐藏后将时间推进 60 秒、接口结果改为 v2/v1，再显示。接口仍只调用 1 次，页面仍为 v1；随后卸载再挂载才发出第 2 次请求并显示 v2/v1。
- 建议：保留输入草稿，同时向数据面板传递激活状态；查询按激活状态启用，返回时按 staleTime 刷新。应一并暂停隐藏分享页的 60 秒轮询，而不是仅用 CSS 隐藏。
- 验收：未过期返回不重复请求，过期返回刷新，草稿/筛选不丢失；隐藏面板不继续轮询。

#### 问题 2 [P2]：应用响应映射漏掉 projectCode，上传预览使用错误前缀

- 引入提交：`7d3161ea`。
- 位置：`src/lib/artifact-filename.ts:15`；缺失映射位于 `src/services/api/applications.ts:57` 附近。
- 触发：项目配置了下载前缀，例如 `shiyan`，与产品编码不同，用户通过网页上传制品。
- 原因：API 的应用响应已经返回 `projectCode`，但前端 `ApiApplication` 和 `mapApp()` 没有接收/复制它。上传流程从该映射读取应用，再传给文件名预览函数；可选字段导致 TypeScript 未报错。服务端上传则从 projects 表读取正确前缀。
- 复现：真实 `apiListApplications()` 消费带 `projectCode: 'shiyan'` 的响应，再调用真实预览函数，得到 `product_care_v1_b1_stable.apk`，应为 `shiyan_care_v1_b1_stable.apk`。不是命名函数本身失败，而是其上游字段丢失。
- 影响：用户确认的下载文件名与上传完成后的实际名称不同；最终制品归属与内容不受此问题影响。
- 建议：补全 DTO 和映射；增加从 API 响应一路到上传预览的测试，不能只手工构造带 projectCode 的 Application 测试命名函数。

#### 问题 3 [P2]：应用活动查询会扫描其他应用的分享记录，工作量随全站历史增长

- 引入提交：`b04b8a11`。
- 位置：`apps/api/src/routes/audit.ts:47` 至 `:62`。
- 原因：原本按 application_id 读取的查询新增 OR 分支，包含 JSON 成员数组匹配和旧记录的 EXISTS 回退，但没有为成员关系增加相应索引。现有 action 索引只能筛出全站所有分享事件，再过滤其中是否包含目标应用；LIMIT 在此后执行。
- 隔离复现：完整执行当前迁移，生成 300 个应用、9 万条活动（每应用 300 条，10% 为分享事件），查询一个较早更新应用的前 50 条。新旧查询结果一致，计划差异如下。

| ---------------------- | -----------------------: | --------------------------: |
| 应用索引候选           |                      300 |                         300 |

- 边界：这是 **PGlite 隔离实验**，用于确认查询工作量和计划退化，不能将其耗时当作生产 PostgreSQL 16 或真实接口延迟。未生成 9 万个真实制品，也未重跑完整浏览器容量测试。

#### 问题 4 [P2]：发布预览无法识别未跟踪源码的再次修改

- 引入提交：`ca1aa114`。
- 位置：`plugins/artifact-center-mcp/src/publishing.js:52` 至 `:55`，确认比较位于 `:218`。
- 触发：仓库内已有一个尚未 git add 的源码文件，生成发布预览后修改该文件内容，再确认同一预览。
- 原因：`git status --porcelain` 对两次状态都只返回同一个 `?? 文件名`；`git diff HEAD` 不包含未跟踪文件内容，因此 diffSha256 和整个 Git context 均保持不变。
- 复现：独立临时仓库中将未跟踪 `source.ts` 从 value=1 改为 value=2；真实 inspectRepository 返回 `contextUnchanged: true`，真实 confirmUpload 继续调用模拟上传并验证成功（`uploadAccepted: true`）。没有连接真实发布服务。
- 影响：ADR-0023 所约定的“Git 上下文改变后重新预览确认”存在缺口，预览不能完整说明当前源码状态。已复制的制品快照及其摘要检查仍有效，不能将此描述为任意替换待发布文件的漏洞。
- 建议：明确未跟踪源码的处理策略：纳入受控范围的内容摘要，或在预览时拒绝未跟踪源码并提示先纳入版本控制。避免把所有忽略目录和大型构建输出都加入摘要。增加未跟踪文件内容改变的回归，现有测试只覆盖 tracked dirty 文件。

## 代码质量与性能整体评价

- 正向变化：制品类型和命名规则集中复用；分享候选先按权限和项目筛选再分页；收藏失败只回退当前应用；仓库目标精确匹配且遇到多个候选不自动选取；上传确认使用独立文件快照。这些方向合理。
- 主应用列表的 24 条分页、历史页的 30/20 条分页、首屏准备、目录延迟展开仍保留。本次没有发现这些路径恢复成全量制品加载；新增分享候选每页 20 条也改善了之前的全量加载路径。
- 主要维护风险是跨层契约测试不足：projectCode 的函数测试和后端测试分别通过，但中间 DTO 漏字段；页签测试验证了草稿保留，没有覆盖过期刷新；发布测试覆盖 tracked 文件而遗漏 untracked 文件。
- 保留页签需同时设计查询生命周期，不能将“不卸载组件”等同于“缓存策略已完成”。隐藏分享面板还会保持轮询，属于问题 1 的同类边界。
- 收藏 Provider 每次更新都会创建新的 context value 和 toggleFavorite，列表中的 useCallback 因依赖变化不能完全稳定；可用稳定 action 和分离状态减少传播。但本轮未测得这一点造成的独立卡顿，作为低优先级改进，不计入已确认 BUG。
- 前端直接引用 API 目录下的纯模块仍让 Docker/打包边界依赖人工同步。现有 Dockerfile 已补齐本次文件，不能重复报告上次已修复的遗漏；后续可提取明确的共享模块边界。
